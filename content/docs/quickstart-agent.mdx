You have a script or an agent that needs to call a paid endpoint. It holds USDT. It holds **no WBT**, and it does not need any.

You are reading the <NetVal k="networkName" mono={false} /> version of this page.

## 1. Install

<NetCode lang="bash">
{`npm install @x402/fetch @x402/evm viem`}
</NetCode>

## 2. Wrap fetch

<NetCode filename="agent.ts">
{`import { wrapFetchWithPaymentFromConfig, decodePaymentResponseHeader } from "@x402/fetch";
import { ExactEvmScheme } from "@x402/evm/exact/client";
import { privateKeyToAccount } from "viem/accounts";

const account = privateKeyToAccount(process.env.AGENT_PRIVATE_KEY as \`0x\${string}\`);

const fetchWithPayment = wrapFetchWithPaymentFromConfig(fetch, {
  schemes: [{ network: "{{caip2}}", client: new ExactEvmScheme(account) }],
  spendControls: {
    allowedAssets: [
      { network: "{{caip2}}", asset: "{{asset}}", maxAmountPerPayment: "50000" }, // 0.05 USDT
    ],
  },
});

const response = await fetchWithPayment("https://api.example.com/report");
console.log(await response.json());

// The settlement, including the transaction hash:
const paymentResponse = response.headers.get("PAYMENT-RESPONSE");
if (paymentResponse) console.log(decodePaymentResponseHeader(paymentResponse));`}
</NetCode>

That is it. The wrapped fetch makes the request, sees the 402, signs an authorization matching the terms, and retries with a `PAYMENT-SIGNATURE` header. Your code sees one `await` and a 200.

Already paying on other chains? Add their schemes to the same `schemes` array (or use `network: "eip155:*"` for every EVM chain). Nothing else changes.

### Why `allowedAssets` is required

The x402 client has built-in spend controls: by default it only signs for tokens in its own list of well-known assets, capped at $1. Whitechain USDT is not in that list, so without an entry the client refuses every payment with:

```
All payment requirements were rejected by spendControls: only default assets or entries in spendControls.allowedAssets are allowed.
```

The `allowedAssets` entry above opts this one token in, with its own cap in base units (`50000` = 0.05 USDT). Keep the cap: an agent with an unbounded signer and a tool that fetches arbitrary URLs is a bad combination. `spendControls: false` also works, and removes every limit.

## What the agent actually signs

Worth knowing, because you are authorising a token movement with a key:

```ts
// EIP-712 typed data, signed offline. Never broadcast by the agent.
{
  domain: { name: "…", version: "…", chainId: {{chainId}}, verifyingContract: "{{asset}}" },
  primaryType: "TransferWithAuthorization",
  message: {
    from: agentAddress,
    to: merchantAddress,   // fixed by the signature
    value: "10000",        // fixed by the signature
    validAfter, validBefore,
    nonce: randomBytes32,  // single use, enforced on-chain
  },
}
```

The recipient and the amount are inside the signed message, so the facilitator cannot alter either. The nonce is consumed on-chain, so the signature cannot be replayed. The validity window bounds how long it is live. The only discretion we have is whether to submit it.

## Paying by hand

If you are implementing a client rather than using one, decode the 402 to see the terms:

<NetCode lang="bash">
{`curl -si https://api.example.com/report \\
  | grep -i '^payment-required:' \\
  | cut -d' ' -f2 | base64 -d | jq`}
</NetCode>

You will get the `accepts` array. Pick an entry whose `network` and `asset` you can satisfy, sign the typed data above using that entry's `extra` as the domain `name`/`version`, and send it back base64-encoded in the `PAYMENT-SIGNATURE` header. The full field-by-field shape is in the [API reference](/docs/api-reference).

## When it does not work

| Symptom | Cause |
| --- | --- |
| `invalid_exact_evm_payload_signature` | The domain you signed under does not match the token. Almost always a wrong `extra.name` or `extra.version` from the merchant. |
| `insufficient_funds` | The agent does not hold enough of the asset. Check the token balance, not the WBT balance. |
| `unsupported_asset` | The merchant priced the route in a token we do not sponsor on that network. |
| `amount_below_minimum` | Under 0.01 — gas would cost more than the payment. |
| `429` | Rate limited. Back off for the `Retry-After` interval; nothing was broadcast. |
| `503` with `signer_balance_low` | Our gas wallet needs topping up. Retry later. |
| `rejected by spendControls` | The client's built-in allowlist does not include Whitechain USDT. Add the `allowedAssets` entry shown above. |
| Authorization expired | `maxTimeoutSeconds` elapsed between signing and settling. Sign and submit promptly. |
