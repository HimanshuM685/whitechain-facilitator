The hosted instance is free and best-effort. If you need guaranteed capacity, your own gas budget, your own asset allowlist, or you simply do not want a third party seeing your payment metadata, run it yourself. It is one Next.js app and a Postgres database.

Your merchants' configuration changes by exactly one string — the facilitator URL.

## What you need

- Node 22+
- A Postgres database. [Neon](https://neon.tech) works well and the free tier is plenty.
- A funded WBT wallet on whichever networks you enable. **This key signs transactions — treat it as a hot wallet.**

## Setup

```bash
git clone <this repo> && cd whitechain-facilitator
pnpm install
cp .env.example .env     # then fill it in
pnpm verify-assets       # proves the asset registry against the chains
pnpm migrate             # creates payments_testnet and payments_mainnet
pnpm dev
```

Run `verify-assets` before anything else. It checks every allowlisted token's EIP-3009 typehash, decimals, and — the one that silently breaks everything — the EIP-712 domain, against the token's own `DOMAIN_SEPARATOR()`. It exits non-zero on a mismatch and prints the correct values. If it fails, nothing downstream is trustworthy.

## Changing the allowlist

`lib/networks.ts` is the only place addresses live — the guards, the viem clients, the docs components and the `/assets` endpoint all read from it. Add an asset there, then:

```bash
pnpm verify-assets
```

A candidate token must return the canonical EIP-3009 typehash and have a resolvable EIP-712 domain. The script searches candidate `name`/`version` pairs and tells you which one the contract actually signs with, so you never have to guess. See [supported assets](/docs/supported-assets).

## Deploying

Two things to know about topology, because they affect what the guards actually guarantee:

- **Gas budgets are database-backed.** They stay correct no matter how many instances run. This was deliberate: the guard that caps real spending must not depend on process memory.
- **Rate-limit counters are per process.** Each instance enforces its own share, so N instances means roughly N times the configured limit.

### A long-lived process — Railway, Fly, a VM

`pnpm build && pnpm start` behind a reverse proxy. One instance means the rate limits are exactly what you configured. This is the deployment the defaults assume.

### Vercel and other serverless platforms

Works, with one caveat. Add a `vercel.json` so the framework is detected:

```json
{ "framework": "nextjs" }
```

Set `FACILITATOR_PRIVATE_KEY`, `DATABASE_URL`, `MAINNET_ENABLED` and both `NEXT_PUBLIC_*` variables in the project's environment. The `NEXT_PUBLIC_*` ones are inlined at build time, so changing them needs a redeploy. `@neondatabase/serverless` talks to Postgres over HTTP, so no connection pooling to arrange.

The caveat: concurrent lambdas each keep their own rate-limit counters, so **per-IP limits are much looser than configured**. What still holds is the part that matters — the daily gas budget is a database query, so your actual spend stays capped. Set the budgets conservatively and treat the rate limits as a courtesy rather than a control. If you need real per-IP limiting on serverless, move the token buckets in `lib/guards.ts` to a Postgres counter.

### Client IP

Rate limiting buckets on the client IP, which is only as trustworthy as the header it comes from. `clientIp()` prefers `x-vercel-forwarded-for`, `cf-connecting-ip` and `x-real-ip` — all written by the platform and not forgeable past the edge — and falls back to `x-forwarded-for` only if none are present. Behind your own proxy, make sure it rewrites `x-forwarded-for` rather than appending to whatever the caller sent.

Per-payer and per-merchant limits are unaffected by any of this: those addresses come from the signed payload, not a header.

## Operating it

- Watch `/health`. It returns `503` when degraded, so it drops straight into an uptime check.
- Watch the signer's WBT balance. `estimatedSettlesLeft` in `/health` tells you how many payments you can still cover.
- The signer address is public in `/supported`. Anyone can audit your gas spending on the explorer — including you.

## Security notes

- The private key only ever pays gas. It cannot move customer funds: an `exact` payment is one transfer signed by the payer, with recipient and amount fixed in the signature. Worst case per request is one capped transaction.
- Signatures and authorization nonces are never written to the database. Only the metadata the log page shows.
- Error responses do not echo RPC URLs, which may carry API keys.
- Keep the allowlist tight. An open-asset relayer is a gas faucet, and that is the actual attack here — not fund theft.

## Running without the website

The facilitator endpoints are plain route handlers in `app/(facilitator)/` — a route group, so they serve at the bare origin: `/verify`, `/settle`, `/supported`, `/assets`, `/health`.

If you only want the API, delete `app/page.tsx`, `app/docs/`, `app/logs/`, `app/api/`, `components/`, `content/`, `mdx-components.tsx` and `app/globals.css`. Nothing in `app/(facilitator)/` or `lib/` depends on any of them.
